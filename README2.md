# 서약돋보기

> 참고: 이 문서는 초기 기획안이다. 현재 구현 방향은 `AGENT.md`를 우선한다.
> 최신 정체성은 "부산 일반 여행객을 위한 온라인 예약 조건 AI 주의사항 서비스"이며, 사진 촬영/OCR 중심이 아니라 웹사이트 + Chrome Side Panel 확장 프로그램 구조로 개발한다.

부산 해양 레저 여행객을 위한 AI 안전 서약 이해 도우미 & 모두싸인 안심 계약 서비스

> 요트·서핑·스쿠버·제트스키 등 해양 레저를 이용하는 여행객이, 업체가 요구하는 안전 서약서를
> 무심코 서명하는 대신 — AI가 내용을 쉽게 풀어 카드로 보여주고, 이해한 뒤 모두싸인 전자서명으로
> 양 당사자가 안전하게 계약을 체결·보관하도록 돕는 모바일 웹 서비스.

---

## 1. 프로젝트 개요

### 무엇을 만드는가
낯선 여행지에서 "뭔지도 모르고 사인하는" 여행객에게 **이해할 권리와 물어볼 용기**를 주는 서비스.
긴 줄글 서약서를 AI가 중요 항목만 골라 위험도 카드로 재구성하고, 여행객이 각 항목을 확인·동의한 뒤
모두싸인으로 양측 전자서명하여 사고·분쟁 시 법적 증빙으로 활용한다.

### 핵심 철학 (개발 중 항상 지킬 원칙)
- **AI는 "판단"하지 않고 "이해를 돕는다".** 조항의 유·불리를 단정하지 않는다. 쉽게 풀어 설명만 한다.
- **환각 방지가 최우선.** AI 요약은 항상 원문 발췌를 함께 제공해 사용자가 대조할 수 있게 한다.
- **읽게 만드는 것이 본론.** 정보를 소화 가능한 단위(카드)로 쪼개는 것이 이 서비스의 핵심 가치다.

### 대회 맥락 (설계 판단의 기준)
- 주제: "AI를 통해 인간다움을 더 잘 드러내는 서비스"
- 목표: 모두싸인 특별상 (CLM API 활용도 35 / 실용성 25 / 인간다움 15 / AI 활용도 15 / 완성도 10 + 부산·약자보호 가점 10)
- 함의: **모두싸인 API는 서명 버튼이 아니라 계약 생애주기(작성→체결→보관→조회) 전체로 써야 한다.**

## 2. 서비스 구조

### 두 개의 입구, 하나의 공통 몸통
```
[입구 ①] 여행객이 종이 서약서 촬영 ─┐   (메인 · 지금 당장 작동 · 데모 주력)
                                     ├──→ [공통 몸통]
[입구 ②] 업체가 보낸 링크로 진입 ────┘   (확산 후 목표 · 서브)

공통 몸통:
  1. 파싱   : Upstage Document Parse + Info Extract → 서약서 조항 구조화·추출
  2. 이해   : Solar LLM → 위험도 카드(중요 항목 선별 + 쉬운 요약 + 확인 질문 + 원문 발췌)
  3. 확인   : 사용자가 각 카드를 개별 확인 체크 (전부 체크해야 다음 단계)
  4. 체결   : 모두싸인 API → 여행객·업체 순차 전자서명
  5. 보관   : 모두싸인 체결본 영구 보관 + 메타데이터 분류, 분쟁 시 조회
```

### 입구별 차이
| | 입구 ① 촬영 (메인) | 입구 ② 링크 (서브) |
|---|---|---|
| 시작 주체 | 여행객 | 업체 |
| 서약서 형태 | 사진 이미지 | 디지털 텍스트 |
| 업체 사전 준비 | 불필요 | 필요 (템플릿 등록) |
| 개발 우선순위 | **높음 (완성)** | 낮음 (입구만 재사용 증명) |

> 개발 시 몸통(2~5단계)을 먼저 완성하고, 입력 단계만 두 갈래 어댑터로 붙인다.
> 핵심 로직은 한 번만 구현한다.

## 4. API 연동 설계

### 4-1. Upstage Document Parse / Info Extract
- **역할:** 촬영본(이미지) 또는 디지털 서약서에서 조항 텍스트를 구조화하여 추출.
- **추출 대상 항목 예:** 책임 범위, 사고 시 배상, 보험 적용 여부, 취소·환불 조건, 이용 시간.
- **⚠️ 개발 전 검증 필수:** 촬영본(흐림·그림자·기울어짐)에서 파싱 정확도가 실용적인지 실제 샘플로 테스트할 것.
  안 좋은 조건으로 일부러 찍어 넣어볼 것. 정확도가 낮으면 촬영 가이드 UX(밝은 곳·평평하게)로 보완.

### 4-2. Solar LLM — 위험도 카드 생성
- **역할:** 추출된 원문 텍스트를 여행객 눈높이 카드로 재구성.
- **출력:** 아래 JSON 스키마로만 출력 (백틱·인사말 없이).
- **temperature:** 0.2~0.3 (정확성·일관성 우선, 환각 억제).

```json
{
  "summary": "서약서 전체가 무엇에 관한 것인지 1~2문장 요약",
  "cards": [
    {
      "title": "항목 제목 (예: 사고 책임)",
      "level": "high | medium | low",
      "plain": "쉬운 말로 풀어쓴 설명 (2문장 이내)",
      "question": "업체에 확인하면 좋을 질문 한 문장",
      "source": "이 카드가 근거한 원문 문장을 그대로 발췌"
    }
  ]
}
```

- **위험도 등급 기준:**
  - `high` (🔴): 사고·부상 시 책임, 배상 의무, 환불 불가 등 반드시 확인해야 하는 항목
  - `medium` (🟡): 보험 적용 범위, 취소 조건 등 주의가 필요한 항목
  - `low` (🟢): 이용 시간, 준비물 등 일반 안내 항목
- **프롬프트 원칙:** ①유불리 판단·단정 금지 ②원문에 없는 내용 추가 금지 ③중요 항목만 선별(최대 6개 권장)
  ④항목마다 확인 질문 1개 ⑤초등학생도 이해할 쉬운 한국어.
- **`source` 필드의 이중 목적:** (1) 화면 "원문 보기"에 연결 (2) 환각 검증용 대조 기준.

### 4-3. 모두싸인 API — 계약 생애주기 (✅ 문서상 구조 확인 완료)
우리 서비스가 **요청자(Requester)** 계정이 되고, 여행객과 업체를 **참여자(Participant)** 로 넣는 구조.

- **계약 생성:** `POST /documents/request-with-template` — 미리 만든 "부산 해양 레저 안심 서약" 템플릿에
  참여자 정보만 동적으로 채워 서명 요청 발송.
- **서명 순서:** 참여자는 **순차 발송**. 여행객 먼저 서명 → 그다음 업체 확인 서명 (동시 아님).
- **임베디드 서명:** 임베디드 초안 생성 API로 우리 웹 안에서 바로 서명 가능 (외부 이동 없음).
- **서명 수단:** **EMAIL / KAKAO 권장** (연락처 점유 확인 → 법적 증빙력 확보). SECURE_LINK는 점유 미확인이므로 지양.
- **상태 추적:** Webhook으로 서명 완료 등 이벤트를 지정 URL로 POST 수신 → 후속 자동화(알림 등).
- **보관·분류:** 체결본 download URL + 메타데이터(labelIds)로 종류별 분류·조회.
- **제약 주의:** 대량전송 API 없음(반복 호출로 구현). Rate Limit(Standard 분당300/초당10, 파일업로드는 High-cost 분당150/초당5).
- **⚠️ 개발 전 확인:** 해커톤 제공 크레딧으로 임베디드 서명·Webhook까지 열리는지 범위 확인할 것.

## 5. 화면 흐름 (개발 대상)

```
온보딩
  └─ 입구 선택
       ├─ [촬영] 카메라로 서약서 촬영 → 파싱 로딩
       └─ [링크] 업체 링크 진입 → 디지털 서약서 로드
  └─ 위험도 카드 리스트 (🔴🟡🟢 / 항목별 확인 체크 / 원문 접기)
  └─ 전체 확인 완료 → 동의
  └─ 모두싸인 서명 (여행객 → 업체 순차)
  └─ 완료 · 체결본 보관 안내
```

> 상세 와이어프레임은 별도 작업 예정.

## 6. 개발 원칙 (에이전트 준수 사항)

- 위 **핵심 철학(§1)** 을 코드·문안 전반에서 지킨다. 특히 AI 출력 문안이 조항을 "판단·단정"하지 않도록 한다.
- Solar LLM 응답은 반드시 JSON 파싱 후 사용하며, 파싱 실패에 대비한 에러 처리를 둔다.
- 모두싸인 호출은 실패(인증·Rate Limit 429)에 대비해 재시도·백오프를 고려한다.
- 브라우저 저장소(localStorage 등) 대신 상태는 앱 상태/백엔드로 관리한다.
- 데모 시연 흐름(입구① 촬영 경로)을 우선순위로 두고, 그 흐름이 끝까지 매끄럽게 돌도록 완성한다.

## 7. 미해결 과제 (개발과 병행해 다룰 것)

- **업체 서명 유인:** 업체가 왜 서명 요청에 응하는가?
  → 논리: "손님이 안전 수칙을 이해·서명했다는 증거 = 업체 자신의 사고 시 보호책". 발표 방어 논리로 준비.
- **Upstage 촬영본 정확도:** §4-1 검증 미완료. 개발 전 실제 샘플 테스트 필요.
- **모두싸인 크레딧 범위:** §4-3 확인 필요.
- **백엔드/DB 선정:** 서명 세션·상태 저장 방식 확정 필요.
